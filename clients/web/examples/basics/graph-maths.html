The web port of the Python client's graph_maths.py: the whole operator set, not just the four. Every math method beyond add/sub/mul/div — .mod(), .min()/.max(), the comparisons, .midicps(), .distort(), .clip2() … — composes the server's generic BinaryOpUGen/UnaryOpUGen, computed by the same shared core the client uses off the audio thread. So a value computed ahead of time and the UGen on the audio thread agree bit for bit. Nothing here needs Faust: the def does real per-sample maths. The range maps are part of that surface and are shown here too: .linexp() and its five siblings map a signal off one range onto another through the very function the page's own linexp computes with. The vibrato below is the case worth reading — a vibrato is a ratio, not an offset — and its bounds are themselves signals, which a map allows. This is the port where the method form is the point. Where the Python client writes sine(5) * (freq * 0.01), TypeScript has no operator overloading, so it writes sine(5).mul(freq.mul(0.01)). The two emit the same spec JSON, which is exactly what the parity vectors assert.
