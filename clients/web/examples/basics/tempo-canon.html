The web port of the Python client's tempo_canon.py: ten clocks accelerating to ten different tempos, and arriving together — the same piece, voice for voice. A tempo canon: one line, played by ten voices at once, each on a tempo of its own. Every voice starts slow — a beat every one to four seconds — and rushes to somewhere between 8 and 10 beats a second, both drawn afresh every run. They begin as ten unrelated drips, thicken over half a minute into a single band of sound, and every voice reaches its final tempo at the same instant — which is the whole point, and the thing that is awkward to arrange any other way. Why they arrive together. Each voice is a TempoClock of its own, and the gesture is one call: clock.setTempo(target, { over: 30.0, unit: "seconds" }). unit: "seconds" is what makes the ten ramps the same length: a stretch of wall clock, not of beats. The same request in beats would not do it. A beat is a logical coordinate, so thirty beats of a voice rushing to 10 is a far shorter time than thirty beats of one rising to 2 — the ten would finish accelerating at ten different moments, and the piece would dissolve instead of landing. With ten different starting tempos as well, the beat each voice reaches is nowhere near the others; the seconds are the only thing they share, and that is exactly what the call asks for. Nothing about it is approximate either: the width in beats a request in seconds implies is solved in closed form, so a ramp ends on the second it was asked for. Ten clocks, one server. A Session owns a server and as many clocks as the piece has tempos, so this page makes ten. Each is lockTo the server, which puts its scheduling on the engine's own sample counter — and there is one reader of that counter, built by the first clock and shared by the rest. Each also adopts the session, because it is built while the session is ambient: they are in session.clocks, session.start() starts them together, and session.close() closes them. What is different from the script, and it is only the platform: the numeric core is wasm and has to be fetched before anything calls into it (await loadCore(), which a script does not need because the same code is already in the process), writing an envelope on a map is tempoEnv(map, …) rather than map.env(…) because the map is a generated wasm class that cannot grow a method, the engine is the tab's own (Session.embed is this client's live), the calls that reach it are awaited, and the watching loop is a timer rather than a sleeping main thread — a page has no thread to block. Every other line is the call the script makes, in the order it makes it. Build first (./build.sh from clients/web), then serve this directory and open the page.
