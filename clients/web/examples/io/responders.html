The web port of the Python client's osc_responder.py: the client as a hub — what arrives drives what is sent. An OscFunc registers a callback that fires when a matching message arrives, and that callback may send onward: one turns an incoming /onset into a synth, the other re-aligns this client whenever a conductor changes the shared transport grid. Where the reference client binds a UDP port any application can target, a page has no socket to bind: its receiver is the carrier it already has — this engine's connection — so src reads page rather than a host and a port. And nothing outside can send into it, so the sender is the engine itself: a def whose only job is to report its own onsets with sendReply stands in for the script's second socket. The transport half is the same on both sides, because the push comes from the server. Everything below runs on the in-page engine: no server process.
