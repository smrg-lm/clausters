The web twin of the Python client's recording.py: takes drawn while they record, in a page. Every other way audio reaches a picture announces itself — a client sends samples, a peer edits a span and says so. A recording does not: a recordBuf fills a buffer block by block from the audio thread, which is the one place that must never send a message. A host that can map the engine's memory reads the buffer's write frontier and re-summarizes what appeared. A page maps nothing: its samples are its own copy, so there is no frontier to read and nothing to re-summarize. So the server sends the overview instead — /buffer_stream, min/max/energy per bucket, about a hundredth of the audio's bandwidth — and the host folds each report into the pyramid the picture already holds. Nothing about the audio crosses back, and the summary a page draws is the summary a desktop host derives for itself. Nothing in this script asks for it: the fills prop says this buffer is being written, and the host subscribes for the views that need it. Nothing is downloaded either. A take allocated to be recorded into holds silence, so the host asks only what shape it is and builds an empty summary of that length — the picture is the whole of the box it will fill, which is why the axis does not move while it fills. Zoom in (wheel): past what the overview can resolve, the host reads back the span you are looking at — a finer overview of it while a column still holds many samples, and the samples themselves once it does not. So the picture is the same here as in a desktop window, which reads the memory it mapped — the route differs, the drawing does not. That holds while a take is still recording too: everything behind the write frontier is final, so it is read like any other span, and only what is past the frontier is left to the overview — which is the one thing the picture cannot know yet. The last button is the other way a picture changes: a second client — its own connection to the same engine, a peer as far as the server is concerned — silences the middle of the first take and announces the span with /buffer_touch. A desktop host maps those cells and only has to re-summarize them; a page holds its own copy, so it reads the span back (/buffer_getRange over the announced frames, widened to whole buckets) and puts it into both the samples and the summary. Zoom in or out afterwards: the gap is there at every scale, which is what says the summary was patched and not just the run under the eye. The last lane has its own ruler, and that is not decoration: it is eight times longer than the takes, and a navigation group is one window in samples over every lane in it — so two lengths mean two axes. Zoom (wheel) and pan work on whichever ruler or lane the pointer is over, and each group moves on its own. It is the other half of the same question, and the one that is not about recording at all: a take that is finished and too big to download. A page has two routes to a picture and keeps both, because they are cheap in opposite cases — a short buffer is pulled whole and then every zoom is free, while a minute of stereo (23 MB, and a ten-minute take is 230) is drawn from its overview and reads back only the span under the eye. What chooses is the buffer's size, not whether something is recording into it. The overview of a take standing still is asked for (/buffer_peaks) instead of streamed; it is the same blob, folded the same way. Everything runs on the in-page engine: no server process, no socket.
