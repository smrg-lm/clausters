# GUI rendering and interaction procedure

Use a display/GPU and a reserved machine. Record the measured host binary/hash, GPU/driver/backend, native or browser shell, browser version/flags, font, antialiasing, refresh rate, physical viewport and logical scale. Use the revision's existing view example (for example clients/python/examples/views/window.py) from the isolated source, with explicit native-artifact overrides. Provision any client prerequisites in an independent environment; do not use the maintainer's editable installation.

1. Fix a 1280x720 physical viewport at scale 1 for the initial series when supported; record actual values or a revised profile if unsupported. Use one window and a deterministic waveform fixture. Save screenshots for each series.
2. Warm up 10 seconds, then collect three 60-second idle trials without interaction. Record process CPU/RSS, redraws and available frame/presentation counters. Report unavailable counters explicitly. A CPU/RSS sampler is supplied in scripts/sample_process.py; it does not measure GPU/frame latency.
3. Collect three 60-second active trials. Use the same timed action script for each: 10 seconds fixed view, 20 seconds repeated zoom/pan, 20 seconds live updates/playback, 10 seconds fixed view. Record the exact gesture/input driver, rate and data source. If interaction is manual, retain timestamps and label the resulting timing variability.
4. At fixed viewport and visible range, sweep total input size; then at fixed total size sweep visible density and window count. Fix the sizes/rates before capture. Keep data and image quality identical across candidates and use the same action sequence. Record geometry/upload sizes and CPU/GPU time separately when instrumented. GPU timestamps require backend support and must not force unsupported features.
5. Check zoom anchors, clipping, layout, hit testing, edit-back behavior, source changes and window/resource recovery. Compare native/browser behavior using the same host rules and client calls. Browser and device limitations remain visible; an offscreen or headless pass cannot substitute for this check.

Attach raw per-run captures, screenshots and the workload/configuration to gui-device evidence. Frame quantiles must come from frame samples, not suite wall time. Test image correctness alongside any claimed speedup. Without the required real-rendering evidence, leave the step skipped and campaign partial.

Keep the display on and the measured window visible for every trial; unattended blanking invalidates rendering measurements. Count successfully drawn frames, not redraw requests. Require >=20 fps in each active trial, and attach per-run frame counts/durations plus a screenshot, screen-on attestation and renderer identity using the fields in [the combined procedure](combined.md). A paused or intentionally static view is a separate workload, not an active rendering acceptance trial.
