# Audio and GUI interference procedure

This component scenario has required manual execution because audio devices and GPU/display configurations are physical prerequisites. Complete and retain the selected audio and GUI controls before claiming combined coverage. Keep the same source commit, builds, load, sample rate, callback sizes, physical viewport, scale and action sequence across controls and combined trials.

Warm up each condition for 10 seconds. Collect three paired 60-second repetitions of audio only, GUI only and both together, alternating condition order between repetitions. Keep the audio server/driver and GUI driver in the same invocation when sandbox network isolation applies. Record actual PID/binary identities, startup/shutdown commands, ports and cleanup. Reserve the machine so other agents do not compile during capture.

Capture audio deadlines/xruns and output correctness plus GUI frame/interaction behavior, process CPU/RSS and available GPU/upload counters. Retain raw files per condition/repetition. No missing counter becomes zero, and no average replaces an audio deadline miss. Mark unsupported metrics explicitly; if essential device evidence is unavailable, leave the check skipped.

Attach combined-device evidence with controls, raw captures, exact input timeline, thermal/background-load observations, source/fixture hashes and exclusions. Report observed interference separately for audio and GUI. First-run performance figures are descriptive, with no invented cross-machine threshold. Correctness and recovery failures are failures even when average throughput improves.

Before collection, run the instrumented `scenarios/device.json` sweep on the reserved machine. Each level boots a fresh server, warms up for 10 seconds and captures 60 seconds. Stop at peak CPU >=90%, any late block or callback past its deadline. The representative load is the largest safe tested level whose mean CPU is <=35%; no eligible level is a collection error. Preserve every attempted level and its receipts, including the stopping level. Three repetitions select three explicit levels; choose and record a common safe load for the paired controls, rather than comparing conditions at different loads. The sweep selects a load; it does not replace the paired experiment.

Keep the screen powered on, unlocked and the measured window visible for the entire capture. Disable automatic blanking/suspend through the operator's usual settings before starting, and restore them afterwards. The harness does not change desktop settings. Every GUI run must draw at least 20 frames/second over its measured interval; missing counters, a closed window or insufficient frames invalidate that run even if audio counters look good. Retain a screenshot and renderer/backend/driver identity. A headless software browser pass is functional acceptance, never evidence of physical GPU execution or presentation latency.

Passing `gui-device`, `combined-device` and `device-review` attachments require `screen_on: true`, a `gui_runs` array with `frames` and `elapsed_seconds` for each measured run, and `renderer` with `kind` (`hardware` or `software`), `adapter`, `driver` and `backend`. Attach the raw counters supporting each entry. The same renderer identity is required for `web-review`. A software renderer cannot claim `physical_gpu_acceptance`. A JSON assertion is the operator's attestation; the copied captures and screenshot are the reviewable evidence.
