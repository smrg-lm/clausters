# Real-device audio procedure

Use a reserved machine and the prepared source commit. This is a manual required step, separate from the offline benchmark. Read that revision's build/run instructions and record exact commands, feature families, backend, device/driver, sample rate, actual callback sizes and actual thread scheduling policy. Build in the external target directory; use measured native paths rather than another checkout's bundled copies.

1. Select one existing closed audible example from the source revision, retaining its path/hash, command and all input/configuration. Run the server and its driving client in one process invocation/session where network sandboxing applies. Do not change the example to make a missing API appear supported.
2. For each chosen device configuration, warm up 10 seconds and capture three 60-second runs at fixed load. Capture an unloaded control, representative load and a deliberately increasing load sweep. Fix the load increments before running and stop at the documented safe saturation point. Do not change volume or system audio configuration automatically.
3. Retain callback/block timing histograms and backend xrun evidence if available. If a counter is unavailable, record skipped coverage rather than inferring zero glitches from a CPU average. Timing instrumentation requires a replayable patch, bounded preallocated capture and an uninstrumented control. Record sample loss and clock sources. An ear check alone does not establish deadline compliance.
4. Check correct output/scheduling, silence after node.free(), saturation reporting and recovery. Include both def families and feature/ABI seams when making a whole-server claim; use the existing matrix and DSP correctness suites as evidence. Otherwise leave the missing scope skipped.
5. Record per-run raw samples/counters, maximum observed, quantiles with sample counts, deadline budget based on actual frames/sample rate, and separately any loopback setup/results. Review thermal/background load and repeat contaminated trials as newly identified runs, preserving exclusions.

Attach audio-device evidence with exact configuration, profiler/counter versions, raw captures, commands and correctness observations. Passing means the stated procedure and correctness assertions are evidenced; first performance values are descriptive until a comparable reference and noise tolerance are accepted. If essential measurements cannot be collected, leave the required step skipped and report the campaign as partial.
