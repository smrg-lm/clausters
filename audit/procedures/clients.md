# Separate Python and web client audits

Use separate preparation roots, evidence, review and baselines for Python and web. Python is the reference surface and behavior; that does not make Python automatically correct. Both clients bind the same Rust rules and must expose the same capabilities. Record language idioms separately from actual gaps.

For Python, inspect API contracts and signatures, asynchronous def loading/barriers, clocks/patterns/routines without blocking scheduler threads, callbacks, ctypes ownership/ABI matching, package/native artifact resolution, errors and resource cleanup. Run the complete package tests and native parity checks with the measured libraries. Review touched or representative examples against actual supported APIs and run them manually where needed. For signature/call-site analysis provision the revision's pyright tool separately and record its version/output; do not let npx fetch a latest tool silently during a campaign.

For web, build before testing as required by the project. Record actual node/browser versions, native WS binary identities, wasm/bindgen hashes, OPFS/Worker data paths and generated binding vectors. Read API and duplicate examples against the Python reference verb by verb and in the same call order; a similar picture is insufficient parity. Retain unsupported cases and test skips explicitly. Run only the usual single browser unless a release or explicit cross-browser audit calls for more.

For representative efficiency checks in either client, fix the number/rate of scheduled events, command batches and source sizes, warm up 10 seconds and capture three 60-second runs (or a fixed deterministic iteration count for isolated API overhead). Record scheduling error, dispatch latency, allocations/memory and CPU where observable. Separate process startup, encoding, transport and server/DSP costs. Do not attribute server work to a client wrapper. Device/browser timings require raw captures and their clock boundaries.

Attach python-review or web-review evidence with package_coverage keyed by every inventoried manifest in that unit, each with status, reason and retained evidence reference. Retain API/example parity tables, workload scripts, raw repetitions, fixture hashes and configuration. Compare baselines only within the same unit and compatible scope. Missing package coverage, unsupported required behavior or unavailable critical metrics remain partial/failure, not an aggregate pass inherited from the component campaign.
