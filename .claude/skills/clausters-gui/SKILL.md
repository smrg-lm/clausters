# Developing the Clausters GUI track

A system of graphical elements **built and driven from a dynamic language at runtime** — the way sclang builds Qt widgets — not a GUI compiled into the clausters server. This skill is the **development map of the crate**: its boundaries, its seams, and the invariants that keep it cheap to extend. It is deliberately *not* a usage reference: a script author's surface — the widget catalog, every prop, the event payloads — is `docs/gui-protocol.md` (the wire reference) and the builder docstrings in `clients/python/clausters/gui/guidef.py`. Those enumerate; this explains.

Four documents outrank this one, each on its own subject. `clients/gui/PLAN.md`: milestone staging and the design rationale behind it (the `Gx` labels live only there, never in published docs or in this skill). `docs/gui-protocol.md`: the wire. `docs/architecture.md`: the host's internal structure and the recipe for adding a widget ("The GUI host: structure, and how to add a widget"; the widget map; "The arrangement layer: where it lives"). `docs/decisions.md`: why a non-obvious call went the way it did. Per-element domain knowledge — trigger algorithms, goniometer geometry, LOD crossfade, envelope-shape math — is [[gui-widgets]].

## The crate boundary and how to build it

`clients/gui` is an **independent workspace**, so it can never entangle the core server build: build and test **from inside `clients/gui/`** (`cargo test`, `cargo run --bin clausters-gui`), never from the repo root — from the root, `cargo` resolves the server crate instead and fails spuriously. It links `clausters-core` (a path dependency pulling only `rosc`) for the shared OSC seam, and — with `notation` — `lyon` to tessellate curves. Note what it does *not* link: neither the server crate nor `clausters-notation`/verovio. **The host holds geometry, never the document** — a client engraves the score and sends a semantic display list, the host fits it to the rect and tessellates it, so a second language reuses that renderer by sending the same list. The same asymmetry runs through the whole crate: the samples, the score and the node tree all live elsewhere.

Features: **`font-atlas`** is off by default — it adds a glyph rasterizer (fontdue) and one atlas texture per window so text draws through a real typeface, and it ships **no face**: one arrives through `FontSource` (`--font <path>` natively, `GuiBridge::font` in the page) or is found among the system's. The embedded bitmap face is the **floor**, not a fallback — every entry point in `host::font` asks `atlas::has_face()` first, so the feature compiled in with no face loaded draws exactly what a build without it draws. The one deliberate divergence: `text_size` is continuous with a face and quantized to half-steps of the cell without one (a bitmap glyph's own pixels must stay equal). Whatever the face, the **cell is declared and the face is fitted to it** — a scale rasterizes at the size whose cap height is the body box — so changing the typeface never relayouts a window; what follows the face is the width of a *string*, measured where the string changes. **`midi` is on by default** — the host must paint live notes when it runs standalone with no language client, and the dependency is target-gated off wasm. `standalone` is **off** by default because it links the `clausters` server crate (`embed,realtime`) — that weight is the whole reason the GUI is a separate crate; `standalone-faust` adds the server's `faust` feature so a bundle's persisted FaustDefs reload.

**The element families are features too, and they are on by default**: `notation` (the `score` element and `lyon`) and `patcher` (the `plane`-with-boxes graph view). A feature exists so a build can *drop* a family, never so it has to ask for one — which is why these default on and `font-atlas`/`standalone` default off. What makes dropping one safe is the protocol invariant rather than any new rule: a family compiled out drops its rows from `elements::builtin`, a lookup that misses both the table and the registry is `Unknown`, and `Unknown` is laid out and not painted — exactly how a host older than the def already behaves. The one exception is `patcher`, whose wire name `plane` is shared with the scroll workspace: without the family, a patcher node reads as the workspace it also is.

`check-features.sh` is that matrix's runner, the sibling of the server's `.claude/skills/feature-matrix/check.sh`: clippy, rustdoc, the wasm gate and **the suite** over the floor, each family alone, `font-atlas` and `standalone`. Run it whenever you touch anything feature-gated. It includes the suite because clippy type-checks test code and never runs it, and a family gated out of the code while its tests stay in is a test that compiles and fails — which is exactly what the first run found.

`check-wasm.sh` is the **build gate, not a convenience**: it compiles `--lib` for `wasm32-unknown-unknown` so no later change can silently re-couple the agnostic core to native I/O. Run it whenever you touch `src/host/`. The browser bundle itself is not built here — `clients/web/build.sh` compiles this crate's wasm-bindgen surface alongside the engine and the core codec and stages the whole servable package.

## Architecture in one screen

`clausters-gui` is **two roles in one process**:

- a **GUI host for the languages** — it owns the windows, the widgets and the GPU, and exposes the widget protocol;
- a **client of the clausters server** — it reads buffers, buses and the node tree and sends control, exactly as [[clausters-python]] does.

Three legs, then: script ↔ audio server (the ordinary OSC control), script ↔ gui host (the widget protocol), gui host ↔ audio server (the gui as a client). A **bound** widget bypasses the script entirely — its value flows straight from the host to the audio server, the same idea as the server's MIDI bindings, and the reason latency does not depend on the language's scheduler.

### The protocol invariants (these are what you must not break)

- **OSC is the single encoding everywhere**, through the one `clausters_core::osc::decode_packet` door. Never a second decoder, never a side channel.
- **A GuiDef is JSON inside one OSC argument**, exactly as a SynthDef rides `/def_send synth`: JSON is the payload, OSC is the framing. serde's number handling keeps ids `i32` and control values `f32` across the wire — preserve that int/float distinction on the client side too, or a widget silently reads the wrong type.
- **Construction is declarative, updates are incremental.** A GUI is a *def*: the whole tree is built in one message, then live widgets are mutated one at a time. No per-widget construction chatter.
- **A widget is added by extension, never by protocol change.** `host::guidef` parses the *generic* node (`{id, type, props, children}`) and keeps it open; `host::widget` is the *renderer's* typed interpretation of it. Adding a widget means a `WidgetKind` arm plus a renderer — but check first whether it is a widget at all: a new view *of a signal* is a configuration of `host::elements::signal` (another presentation, source or capability), not a new kind. An unknown type is laid out but not painted, which is exactly the behavior an older host should have against a newer script. If a change seems to need a new `/gui_*` address, that is the signal to reconsider: new event *payloads* on `/gui_event` are the established way (the edit-back pattern in [[gui-widgets]]).
- **The widget tree reuses the scsynth node-tree shape verbatim** — client-allocated ids, subtree free, `/g_query`-style introspection (see [[scsynth-osc]]). The address family is the generic `/gui_*`, not `/win_*`, because a root may be an embeddable panel rather than a window.

### Editing without owning the data

Holding no document does **not** make the host a passive viewer — its editing widgets are as real as the read-only ones. The host owns the gesture and draws the edit as it happens, reasoning geometrically about it: a dragged note moves up the staff in whole diatonic steps *and has its ledger lines re-derived* from the staves it reads back out of the engraving. What it emits on release is the edit as an **intent** — `"transpose" id steps`, the new break-points, the clip's new placement — for whoever owns the data to apply and send back as a fresh drawing.

That split is what lets the pattern generalize: the host can host editing for data it cannot interpret, which is why one renderer serves every language. Two consequences worth carrying. An edit that the host cannot validate is **opt-in and says so** — a `score` page is read-only until `editable`, since offering a gesture no driver will fulfil is worse than not offering it, while *inspecting* a page (selection, the `"element"` click) is never gated that way. And the intent must be expressed in the **owner's terms, not the screen's**: diatonic steps rather than a pixel delta, because the client's editor transposes by steps and a coordinate would have to be read back through the engraver's frame. The pattern's per-widget detail is in [[gui-widgets]].

**Standalone** mode closes the loop: a saved GuiDef paired with its GraphDefs (a *bundle* in the data dir, plus a root `name`/`boot` and widget `bind` props that make the tree self-driving) is booted against an embedded server with no language client at all. It is why the host cannot assume a script is attached — the reason `midi` is a default feature, and the reason a gesture must exist host-side and not only as a client helper.

### The three transports

The host's default port is **57210** (clear of the server's 57110/57120), on **UDP and TCP alike** — like the audio server, TCP is accepted by default (`--no-tcp` opts out, `--max-frame` sets the ceiling, default 16 MiB), and the Python `GuiHost` **connects over TCP by default**, so a `/gui_def` tree with its blobs — the largest payload in the system — is not bounded by a datagram. **WebSocket** (`--ws`, default 57220) is the opt-in third carrier, mirroring the server's own: one OSC packet per binary message, the leg the TypeScript client uses to drive a *native* host from a page. All three land on the same single-threaded front behind `transport::ClientId` and one reply seam — that seam is what let TCP and WebSocket be added without touching the protocol, so keep new carriers behind it. The *client* leg is the separate `ServerLink` enum, whose variants follow the deployment rather than the carrier: `Udp` natively, `Embed` in-process under `standalone`, and in the browser `Ws` to a separate server or `Page` to the in-page worklet engine.

## The platform seam (`src/host/`)

The host is a **platform-agnostic core with two thin shells**. Which side a module lives on is the crate's load-bearing decision, so read the module docs in `src/host/mod.rs` — they state the seam per module — rather than inferring from file names.

- **The pure core (compiles to wasm unchanged)** holds everything that is logic rather than I/O: the generic parse and the typed tree, the registry (node-tree shape: parent/children, subtree free, redefine-replaces), layout, the triangle-mesh `Painter` with its embedded bitmap font, the theme's color roles, the per-widget models (controls, meters, node tree, envelopes, timelines, tracks, patchers, rolls, keyboards, text editing, score geometry) and the **signal element** (`host::elements::signal`), which is every view of a signal as one model — a presentation × a source × the capabilities over it, with the six wire names (`waveform`, `plot`, `scope`, `spectrum`, `spectrogram`, `phasescope`) as presets of it, `frame` — **the one per-window render both shells call**, which is why the browser is pixel-faithful by construction — `interact` (hit-test + value mutation) and `gestures` (the one press→drag→release→wheel state machine), plus the protocol dispatch in `mod.rs`.
- **I/O behind small traits** — the seam itself: `Transport` (send OSC to the audio server), `DefStore` (named-GuiDef persistence), `BulkLoader` (resolve a `path`/`cache` to samples or a pyramid), `BusSource` (per-frame bus reads, plus the tap reads, sample rate and sample clock), and — only in a `font-atlas` build — `FontSource` (the bytes of the typeface: a mapped file natively, fetched bytes in the page).
- **The native shell** implements those traits over sockets, the filesystem and mmap — including a read-only map of the server's `--shm` segment (validating `MAGIC`/`ABI_VERSION`) — and adds the winit + wgpu windowed front under `host/gui/`, split by role (state and event loop, window lifecycle, the audio-server reply leg, thin input adapters onto the shared gesture machine, live MIDI painting).
- **The browser shell** is `web.rs`: a wasm-bindgen `GuiBridge` (`feed`/`def` push OSC packets in, `poll` drains events out, `connect_server(url)` attaches a WebSocket link). Bulk resolves as URLs through `fetch`; buses arrive over `/bus_stream`. `crate::gpu` picks WebGPU where a real adapter exists and **falls back to WebGL2** otherwise.

**A leaf is two files, and the split is by who asks.** `host/elements/` is the surface the passes see: an `impl Element` answering `set`, `needs`, `natural`, `slot`, `body_role` — one method per question the frame, the gesture machine or a `/gui_query` puts to it. `host/graphics/` is what that element *knows*: the data shape, the geometry, the drawing over a `Draw`, the hit-test primitives that invert it. The boundary is negative and that is what makes it useful — a model names no `Host`, no `Element` trait, no props map, no OSC and no device, so it unit-tests without a window. The dependency runs one way (an element reads its model), and the tree is parallel rather than nested because the cardinality does not match: `controls` draws eight elements, `pianoroll` draws the `notes` leaf *and* a clip's roll body, `track` draws a container and no element at all. An element is a file, or a directory when it needs one — `elements/signal/` is the only one so far, with a child per trait question.

**Two rules keep the seam honest.** First: *a gesture is implemented once, in `gestures`* — the two fronts drove divergent drag machines once, and every editing feature had to be written twice until they were merged; the machine mutates the host through the `interact` doors and returns effects for the front's sinks. Second: *native-only I/O never leaks upward* — if a core module needs the clock, the samples or the wire, it takes a trait, and `check-wasm.sh` proves it.

**Bulk data rule:** large payloads move through **local shared resources** (mapped files, the shm segment), never re-encoded over OSC; the network primitives (`/buffer_getRange`, inline blobs) are the async fallback — and the browser's only path. A client builds a peaks cache and hands the host the file; a server buffer is exported to a mapped file or pulled over the leg. Shared analysis (forward FFT, the peak pyramid, windows) lives **once** in `clausters-core`, reused by host, server and clients alike.

## Where new logic goes (decide this before writing it)

Every new compute function gets an explicit placement decision, recorded with the work:

- **General** — plausibly useful to another client from Python, or to a future server feature — goes to `clausters-core`, with a `clausters-ffi` export when a non-Rust client will consume it (and the `CORE_ABI_VERSION` bump that implies). Peaks, the forward FFT, the windows, correlation and Lissajous geometry, the hertz↔mel/bark scales, the bar/beat reads and the envelope shapes all took this path; the notation layer took it wholesale into `clausters-notation`.
- **Display-only** — hit-testing, tick spacing and label fitting, trigger alignment of a drawn window, clip and lane geometry, navigation and group state — stays gui-side.

The tell is not "is it math" but *would anything outside a window ever call it*. An FFI export can also be deliberately **deferred** until a client actually needs it, rather than exported speculatively.

## The reusable rendering machinery (crate root)

What is written **once against `wgpu`/WGSL** runs natively and in the browser unchanged. These modules are windowing-agnostic; `native.rs` is only the standalone demo harness for the `waveform`/`spectrogram` binaries — the real windowed front is `host/gui/`.

| Module | Role |
|---|---|
| `viewport::View` | the visible window in `f64` sample units — `full`/`zoom(factor, anchor, total)`/`pan`/clamp; pure, unit-tested, renderer-agnostic |
| `peaks` (re-export of `clausters_core::peaks`) | resolution-matched peak LOD + its cache: `Pyramid`, the multichannel `MultiPyramid`, `level_for(spp)`, `column` (min/max) and `column_ms` (the per-bucket mean square, stored as energy so levels combine exactly — `has_mean_square` is false for a cache written before CLPK v3), the CLPK cache format (one file for all channels, a mono cache being one channel) |
| `spectrogram::Stft` | windowed-FFT time-frequency analysis (FFT from `clausters_core::fft`) with the same cache shape, plus `FreqScale`, the renderer and the view |
| `waveform` | the audio data (raw samples + a peak pyramid per channel) and a navigable view's vertical state. **No pipeline**: its picture is triangles through `host::graphics::signal::trace`, the one renderer of a signal against time, and the render regimes and the level crossfade are a per-frame *data* choice |
| `gpu` | device/surface bring-up shared by every front; WebGPU with the WebGL2 fallback on wasm |
| `view` | the `TimelineView` trait both heavy views implement |
| `bytes` (crate-private) | the flat little-endian `f32` cache layout, mmap-ready |

### The graphics knowledge that governs them

- **The one rule: never resolve the signal finer than the screen.** All work is driven by `samples_per_px = visible_len / render_width_px`, never by buffer length. The waveform expresses it by picking a resolution-matched LOD per frame; the spectrogram expresses it *structurally* — one texture sample per pixel, so GPU cost is constant regardless of zoom.
- **Two rendering shapes, both used here.** (a) *Geometry* — the waveform, the flat widget chrome and the tessellated score all build triangles per frame into `paint::Mesh`, bounded by `render_width_px` rather than by the buffer. A signal against time is drawn in exactly **one** place (`host::graphics::signal::trace::draw_channel`): a second destination for the same picture is a second implementation, and the two did drift before they were merged. (b) *Full-screen quad + texture sample* — the spectrogram uploads the STFT once as a 2D texture (x=frame, y=bin) and the fragment shader samples it, so the GPU's linear filtering gives free resolution-matched downsampling on zoom-out.
- **Uniforms are free, recompute is expensive — put every display control in the shader.** Colormap, dB window and contrast, the frequency-axis mapping (linear/log/mel/bark) and the frequency zoom/pan (a *second* `viewport::View`) all change live at zero CPU cost. Only window size, hop or sample rate force a `Stft::compute`.
- **Anchor-preserving zoom is the core navigation math**: `pivot = start + len*anchor`, scale `len`, keep `pivot` fixed, clamp. The frequency axis keeps its window in **display coordinates**, not in bins, so the cursor anchor holds in every scale — the nonlinearity lives entirely in the shader's display→bin mapping.
- **Two pixel spaces, and a heavy view lives in the physical one.** `render_width_px` is always **physical**: the resolution rule is against the screen's real pixels, so a view driven by logical widths comes out blurry or over-detailed. The *chrome's* space is the separate, logical one: the wire declares logical pixels and a per-window `ui_scale` resolves them (see the sizing model below). A heavy view's samples-per-pixel arithmetic stays physical regardless.
- **WebGL2 is the compatibility floor.** The wasm bundle compiles both backends and picks at runtime, so keep new GPU work inside what WebGL2 can do — vertex/fragment pipelines, uniform buffers, filterable textures; **no compute shaders, no storage buffers**. Heavy numeric work runs on the CPU in `clausters-core`. naga translates the WGSL (including user `canvas` shaders) to GLSL ES; a non-translatable shader degrades through the existing error scope, unpainted, no panic.

### The analysis behind the views

- **The peak pyramid is mip-mapping for 1-D audio.** Level 0 stores `(min, max)` per `base_bucket` samples; each higher level halves resolution; `level_for(spp)` picks the level whose bucket matches one pixel column. Three regimes by `samples_per_px`: a polyline through raw samples when a sample is wider than a pixel, exact per-pixel min/max below `base_bucket`, the matching pyramid level above it. The pyramid is ~2× its level-0 size and is a **cache** (memory or file, mmap-ready), the way editors keep an overview file.
- **The STFT is the time-domain analogue**: a windowed FFT every `hop` samples yields `n_frames × n_bins` magnitudes, normalized over a fixed dB reference and stored the same way. FFT and window correctness patterns belong with [[ugen-dsp]] and [[audio-testing]].
- **Live views** read a control bus per frame — from the shm segment natively (zero messages; see [[realtime-audio]] for the shared bus and the embed ABI) or from `/bus_stream` in the browser. Audio-rate data comes from the server's **audio taps**: `/bus_tap` routes a bus into a pre-allocated ring in the segment, with `/bus_tapStream` → `/bus_tapStream.reply` as the browser and headless sibling. The playhead reads the segment's `sample_clock` natively and `/clock_query` per tick in the browser.
- **Heavy views must never reimplement DSP the server owns.** The server already carries the spectral chain; host-side analysis is only what plotting needs, and it comes from `clausters-core`.

## The Python leg, and the arrangement it serves

Every host feature **lands implemented through `clients/python/clausters/gui/`** — that is the acceptance surface, not an afterthought: each widget gets a builder, each protocol verb a client call, and the module reuses the existing OSC encoder rather than a parallel one. Building a tree is host-agnostic; only the client object knows how to talk to a host. Events dispatch through the same `OscFunc` responder model the audio client uses. The examples in `clients/python/examples/gui_*.py` each demonstrate one capability end to end, and a milestone is not closed without one.

Above that sits **the arrangement** (`clausters.form`) — the client-side layer that places elements in time, groups them recursively and renders them — with the **multitrack editor** (`clausters.gui.Editor`) as its view over the `track`/`clip` widgets. When you work on those widgets you are implementing that model's view, so the project's vocabulary rules bind here: an element is **rendered**, never "realized"; a widget is **freed**, never "destroyed"; a group's two kinds are **concrete** (related in time) and **logical** (related by processing); `form` is a code name that never appears in prose. `docs/architecture.md` ("The arrangement layer: where it lives") says what lives where.

**E2E sandbox rule (non-negotiable):** the Bash sandbox isolates the network between invocations — run the host and the Python client in the **same** invocation (host in background with `&`, then the client, then kill). GPU-free logic (navigation math, peaks against brute force, FFT/STFT localization, cache round-trips, parse/layout/fetch/node-tree models, gesture dispatch over a JSON-built host) stays in the crate's `cargo test`; the window binaries need a display and a real adapter; `--headless` runs the protocol with no display.

## Layout: a GuiDef is an app shell, not a pile of widgets

Composing a window is a design act, and the rules are few enough to keep:

- **Size on the main axis is `h`/`w` (fixed logical pixels) or `weight` (a share of the leftover, default 1) — there is no `height`/`width` prop.** An unknown prop is *silently ignored*, so a control strip written `panel(..., height=48)` keeps `weight=1` and splits the window evenly with the main view.
- **Chrome is a fixed strip; the work surface fills.** A transport, toolbar or status bar takes a fixed `h`; the editor or plot beside it takes the default weight and dominates. Use `weight` to divide two work surfaces, `h`/`w` only for chrome.
- **A view bigger than its area goes in a `scroll`** — give it the virtual content area and size the child to it; never place boxes at fixed positions that fall off a fixed window with no way to reach them.
- The layout math is testable without a GPU (layout → rects), but the **judgement is on you**: when you touch an example, check that the main view dominates, the chrome stays thin, and nothing lands off-screen.

### How big a widget is (the sizing model)

**The whole sizing model has landed** (the L track's L6-L8): the numbers are roles of one table, a widget knows how big it wants to be, and the wire's own lengths are logical units one scale per window resolves. `clients/gui/PLAN.md` records what each milestone departed from in shipping.

- **Size by role, not by literal** *(landed)*. The metrics table (`host/metrics.rs`) is the peer of `host/theme.rs`, with the same rule L1 fixed for color: no layout or paint site names a number, it names a role (`pad`, `gap`, `margin`, `indent`, `control_h`, `track_thick`, `handle_thick`, `ruler_h`, `ruler_w`, `header_w`, `divider_w`, `point_radius`, `hit_slop`, `text_scale`, `caption_scale`, …). Defaults come from one quantized modular scale over the font cell, and the table is **constant** — the scale generates the defaults, it is never arithmetic on a frame. It lives on the `Host` beside the theme and is **passed** (`FrameInputs::metrics`, a `&Metrics` beside a draw function's `&Theme`, `host.metrics_for(def_id)` on the hit-test side), never read from a global, because each window resolves its own table. What it deliberately does *not* hold: a widget's own interlocking structural geometry (the patcher's box/port series, the roll's key gutter and lanes, the score's staff step) and sub-pad optical nudges — a role earns its place when more than one widget means the same thing by it.
- **One `scale` key is the whole density surface** *(landed)*: `[gui.metrics] scale = …` (or `GuiBridge::metrics(json)` in the browser) regenerates the table at another density. No size tokens on the wire, no per-widget density — and it covers the table, not a widget's own `text_size` prop.
- **A widget declares its natural size**, a pure function of the metrics per `WidgetKind`, `None` on an axis meaning elastic. No measurement pass and no constraint solver: the one-pass boundary L2 fixed holds unchanged.
- **A container may hug its content** *(K11)*. `hug` on a `window`, a `panel` or a `stack` makes its natural size the composition of its children's (`Widget::hug_size`: a row sums along its axis and takes the largest across it, a col the other way round, a grid counts cells, a stack takes the largest of every page) — one bottom-up walk over the same pure functions, asked of the whole subtree, with elastic propagating so a plane or a heavy view inside still hands its axis back. On a root it sizes the window itself, which is the one half a page has no equivalent for (the element owns its box). **What a size may read is fixed by where the value is resolved**: a prop that settles at a mutation point (a label's text, a menu's options) may size a hugging container through `Element::hug`, a *value* never sizes anything through any door — so no stream of values can relayout a window, and outside a `hug` nothing reads content at all.
- **Main-axis resolution order:** explicit `w`/`h` → explicit `weight` → natural size → a share of the leftover. Explicit `weight` beating the natural size is what still lets a script stretch a button.
- **The wire is logical; the host resolves once.** The declared `w`/`h`/`x`/`y`/`margin`/`gap`/`text_size` are logical pixels, scaled by one `ui_scale` per window that the **shell** writes (`Host::set_ui_scale`) — natively winit's `scale_factor`, re-armed on `ScaleFactorChanged`; in the browser the page's `devicePixelRatio`, carried by `GuiBridge::resize(defId, w, h, scale)` — because the core may not touch a platform API and `check-wasm.sh` proves it. `Metrics::resolved` turns the logical table into whole physical pixels **on scale change**, never per frame, and resolving at scale 1 is the identity.
- **Chrome is logical, a navigable plane has its own units.** Inside a `scroll` workspace the wire's lengths are content units and the plane's `view_zoom` (physical pixels per content unit, written by the pan/zoom gestures) turns them into pixels — `layout::Space` carries that seam. The scale enters as the **default zoom**: `ScrollView::zoom` falls back to the window's `ui_scale`, because a plane's content unit is a display unit; a named zoom is literal. A view whose content unit is *data* (samples, semitones, staff steps) keeps its own window and never sees the scale. **A zoom is an enlargement**: a placement carries the size table it is drawn with (`Placed::metrics`, the host's table through `Metrics::at` at the placement's scale) and the layout measures with the same one, so a scrolled box's lengths, roles and text carry one factor — `layout::Space` is the window, a plane's content units, or the inside of a scrolled child. A plane's content extent is measured at its *natural* scale, never the live zoom, or the plane moves while you zoom it. A widget's module-local structural geometry (patch box series, roll gutter, staff step) lives in the physical space with it, and so does `render_width_px`.
- **The bitmap font wants whole steps.** The table's text roles quantize to half-steps of the cell (the reduced caption's rung), so a glyph's own pixels stay equal to each other; a modular ratio applies to spacing and control heights, never to the font. A script's `text_size` prop is the number it sent, scaled but not re-quantized.

## Conventions

- Build and test from `clients/gui/`; keep it `cargo fmt --check`-clean and clippy-clean, native **and** `wasm32` (`check-wasm.sh`), and across the crate's own features (`check-features.sh`). Code, comments, strings and tests are English.
- `Gx` milestone labels stay in `clients/gui/PLAN.md` only.
- Markdown in this repo is **single-line paragraphs and list items, no hard wrap** (tables and code blocks exempt).
- **Closing a GUI milestone** means more than code: a clear commit message and the `clients/gui/PLAN.md` checkbox; that file's design sections refreshed if the rationale moved (promoting anything settled to `docs/clients.md`); `docs/gui-protocol.md` updated when the wire grew; developer and user docs where the change touches them; a commented example -- also the manual-test surface, where new human-visible behavior gets checked by eye; a `docs/decisions.md` note only for a non-obvious choice ([[documentation]] for placement).
